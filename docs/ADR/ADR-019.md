# ADR-019: OrbStack as the container engine instead of Docker Desktop

**Status**: Accepted · **Re-verified**: 2026-08-23 — still true, one framing correction below
**Date**: 2026-08-21
**Decided by**: Lab foundation increment (001-lab-foundation-bootstrap), acting on P0 plan §10
**Evidence**: specs/001-lab-foundation-bootstrap/research.md — environment re-measurement, 2026-08-20

## Context

The P0 plan §10 names OrbStack as the lighter alternative to Docker Desktop for the container
runtime. Measured on the target machine (2026-08-20):

- OrbStack is **already installed** (`/Applications/OrbStack.app`, `orb`, `orbctl` on PATH).
- Docker Desktop is **not installed**.
- Docker Desktop's VM carries materially higher idle memory/CPU overhead than OrbStack's.
  (At the time this was written, Principle VII made P0 §12.3 a budget **gate**. That gate was
  removed on 2026-08-23 — see the re-verification below. The overhead argument stands on its own.)
- Docker Compose **v5.1.2** is available through OrbStack and is the measured toolchain all
  compose work in this increment targets.

## Decision

OrbStack is the container engine for the Lab. All `docker` / `docker compose` commands in scripts,
runbooks, and verification assume the OrbStack-provided CLI and socket.

## Consequences

- Lower VM overhead, and zero new installs — the engine is already
  present (Principle IV: no dependency added without justification today).
- Scripts probe the Docker socket generically (`docker context ls`, socket probe), so a future
  engine swap does not require script changes — only this ADR's successor.
- Known behavioural difference to watch: `mem_limit` is a legacy compose key; whether it is
  honoured on Compose v5.1.2 under OrbStack is **measured, not assumed** — see
  `scripts/verify-data-layer.sh` assertion 6 and research R4. If measurement shows it ignored, a
  follow-up ADR records the switch to `deploy.resources.limits.memory`.

## Measurement (2026-08-21, Compose v5.1.2 on OrbStack)

`mem_limit: 1536m` **is honoured**: `docker inspect` on the running container reports
`HostConfig.Memory = 1610612736` bytes (exactly 1536 MiB), and `scripts/verify-data-layer.sh`
assertion 6 passes reading the limit back from the container. No switch to
`deploy.resources.limits.memory` is required; the verification continues to guard against a
silent regression on any future Compose upgrade.

## Re-verification 2026-08-23

`mem_limit: 1536m` is still honoured; `docker stats` reports the container using **77.6 MiB** of its
1.5 GiB cap. The OrbStack VM's own host RSS was measured between **292.5 and 484.5 MiB** across the
session — elastic, and the figure the machine actually pays. Note for anyone measuring later: the
guest figure (`docker stats`) and the VM's host RSS must **never be summed**; they are two views of
the same memory and move in opposite directions.

The §12.3 memory **gate** was removed on 2026-08-23 (constitution v2.1.0). This ADR is unaffected:
the reason for OrbStack was never the gate, it was that the engine was already installed and is
lighter. Manual memory steps now live in `docs/runbooks/memory-check.md`.

## Alternatives considered

- **Install Docker Desktop** — rejected: heavier against the budget, and a redundant second engine
  on a machine that already has one installed.
- **Rancher Desktop / colima** — rejected: same redundancy argument, with no compensating benefit.
