# ADR-021: The native MySQL `root` account stays password-less — §8 Item L is optional, not a prerequisite

**Status**: Accepted
**Date**: 2026-08-21
**Decided by**: Operator decision, recorded by the lab foundation increment (001-lab-foundation-bootstrap), acting on P0 plan §8 Item L
**Evidence**: specs/001-lab-foundation-bootstrap/tasks.md T038 — local audit, 2026-08-21

## Context

P0 plan §8 Item L asks the operator to set a password on `root@localhost` of the native MySQL 9.1
service (Homebrew, `127.0.0.1:3306`) that hosts the production snapshot. It is marked 🟠 —
important, and explicitly **not** one of the 🔴 non-waivable items (only Item A, FileVault, is
that). Neither the constitution nor the governing core plan v2.0 mentions a root password, and no
checkbox in P0 §13 depends on it.

Measured on this machine, 2026-08-21 (T038 audit):

- `root@localhost` uses `caching_sha2_password` with an empty `authentication_string`.
- **31** project `.env` files under `~/Projects` connect as `root` with an empty password.
- Setting a password breaks all 31 unrelated local projects until each `.env` is updated by hand,
  and keeps breaking new ones on every fresh clone.
- The machine is a single-operator workstation: one human account, no shared or remote access,
  `bind_address = 127.0.0.1` so 3306 is not reachable off-machine.

## Decision

`root@localhost` **stays password-less**. Item L is downgraded from a scheduled human prerequisite
to an **optional hardening item at the operator's discretion**.

- Item L does **not** block المرحلة 3, and it does not block any later phase.
- No spec, plan, task list, runbook, or verification script may treat a root password as mandatory
  or fail on its absence.
- المرحلة 3's Item C is unaffected: the `GRANT` is still run interactively as `root`, and root
  credentials are still never written to any file.

## Consequences

The compensating controls that were already in force remain **binding and unchanged**:

- **FileVault (Item A, 🔴)** — untouched by this ADR and still non-waivable. It is what protects
  the 2.2 GB snapshot at rest.
- `bind_address = 127.0.0.1` — the snapshot host is not reachable from the network.
- `root` is never stored in any file, `.env`, or connection config (المرحلة 3, §أ). The Lab
  connects **only** as `lab_ro`.
- **ADR-020's eleven-table grant** stays the enforcement boundary for everything the Lab does. A
  root password was never part of that boundary.
- Guardrail checks 9 and 10 still fail immediately if `root` is used from the Lab.

**Accepted residual risk, stated plainly:** any process running as the operator's user — an `npm
postinstall`, a build tool, a compromised dependency — can connect as `root` and read every table
in the snapshot, including `users` (57,482 rows), `orders`, and `personal_access_tokens`
(~24,408 API tokens). Loopback binding does not prevent this; only a password would. The operator
accepts this risk. It is the machine's pre-existing state, not a condition the Lab creates, and it
is unchanged by this program.

**Re-evaluation triggers.** Any one of these flips Item L back to required, and this ADR must then
be superseded:

- A second human account, or shared/remote access (SSH, screen sharing, remote management) on this
  machine.
- The snapshot is loaded onto a machine that is not single-operator.
- A project on this machine begins running untrusted third-party install scripts against the same
  MySQL instance.
- Port 3306 stops being loopback-only, or the snapshot is exposed to any service that is not
  loopback-bound.

## Alternatives considered

- **Set the password and update all 31 `.env` files** — rejected by the operator: large blast
  radius across unrelated local projects, recurring maintenance cost on every new clone, and no
  gain against the actual threat model of a single-operator, loopback-only workstation.
- **Create a separate password-protected admin account and leave `root` as-is** — rejected: the
  password-less `root` path still exists, so it buys nothing.
- **Socket-based authentication for `root` (`auth_socket`)** — not evaluated; it would first need
  verification that the plugin ships with this Homebrew MySQL 9.1 build. Left as the preferred
  option to revisit if a re-evaluation trigger fires, since it would harden the account without
  touching any `.env`.
