# ADR-021: InjazEdu MySQL is read-only by architecture, not by database privilege

**Status**: Accepted
**Date**: 2026-08-21 · **Revised 2026-08-23** — guard 3 splits into two allowlists (see below).
**Revised 2026-08-26** — `question_result` moves from the copy allowlist to the profile allowlist,
making the split **ten copyable / seven profile-only**. See ADR-022 for why.
The decision itself (application-enforced, `root`, no `GRANT`) is unchanged by both revisions.
**Supersedes**: the 2026-08-21 `lab_ro` framing
**Decided by**: Operator
**Evidence**: local audit 2026-08-21; `docs/plans/lean-development-process.md`

## Context

The Lab reads a local copy of the InjazEdu production database and copies what it needs into its own
PostgreSQL. The question is what stops it writing to, or over-reading, that source.

An earlier design answered this with a dedicated MySQL account (`lab_ro`) holding `SELECT` on exactly
eleven tables, issued interactively by the operator with `root`. That design was withdrawn. It
required an operator gate on every environment, a committed grant file, re-issuing the grants on
every snapshot refresh, and a verification script built around privilege enumeration — a significant
amount of standing machinery for a single-developer local project.

Measured on this machine, 2026-08-21:

- MySQL 9.1.0, Homebrew, `bind_address = 127.0.0.1`. `root@localhost` uses `caching_sha2_password`
  with an **empty** `authentication_string`.
- **31** project `.env` files under `~/Projects` connect as `root` with an empty password. Setting a
  password breaks all 31 until each is updated by hand, and keeps breaking new ones on every clone.
- Single-operator workstation: one human account, no shared or remote access.

## Decision

**The Lab connects to InjazEdu MySQL as `root` with no password**, and the read-only direction is
enforced **in the application**, not by the database.

```env
INJAZEDU_DB_DATABASE=injazedu
INJAZEDU_DB_USERNAME=root
INJAZEDU_DB_PASSWORD=
```

No `lab_ro`. No additional MySQL account. No `GRANT`. No operator gate. No change to the
authentication model.

Three guards carry the guarantee, each of which must block with the other two removed:

1. **No write target.** The `injazedu` Laravel connection is configured `'write' => ['host' => []]`.
2. **A query listener.** Any statement on that connection whose first keyword is not `SELECT`,
   `SHOW`, `DESCRIBE`, or `EXPLAIN` throws before it reaches the database.
3. **Two allowlists** (revised 2026-08-23). `SourceReader` refuses, by name, any table outside the
   union of:

   - `config('lab.source_tables')` — the **ten** tables that may be **copied into** the Lab.
   - `config('lab.profile_tables')` — **seven** additional tables readable for **aggregate profiling
     only**, never copied: `course_user`, `course_order`, `orders`, `user_roles`, `roles`,
     `book_course`, and — since 2026-08-26 (ADR-022) — `question_result`.

   Fifteen tables remain refused in both directions, `users` among them.

## Consequences

- The connection is ordinary and needs no setup ritual. A fresh clone, or a refreshed snapshot,
  works immediately — there is nothing to re-issue and nothing to re-verify at the database layer.
- §14.2 remains fully in force, and the 2026-08-23 split makes it *more* precise rather than looser.
  It was always an **ETL rule** — what may be copied *into* the Lab. Conflating that with what may be
  *read* blocked three of the program's own profiling queries (§6 nos. 15, 16, 18), which answer two
  questions the program cannot proceed without: which table actually records enrolment, and whether
  `course_user` holds students or trainers. Reading a count is not storing a row.
- **The guarantee that carries the weight is unchanged**: no PII column exists in the Lab database,
  proven by `NoPiiInLabSchemaTest` against the schema itself — not by what a query happened to
  select. That assertion is indifferent to how wide the read allowlist is.
- `lab:health` checks 9 and 10 are unaffected. Check 10 targets `users`, which is refused in both
  directions.
- The three guards are covered by three tests (`ReadOnlyGuardTest`, `SourceTableAllowlistTest`,
  `NoPiiInLabSchemaTest`). Removing any guard breaks a test.
- `SNAPSHOT_DB_ROOT_*` no longer exists as a forbidden key, because the split identity it referred to
  no longer exists. The credential in `apps/lab/.env` *is* the administrative one.

**Accepted residual risk, stated plainly.** MySQL enforces nothing here. The application connects
with an account that can write to and read every table in `injazedu`, including `users`
(57,482 rows), `orders`, `certificates.id_number` (national identity numbers), and
`personal_access_tokens` (~24,408 API tokens). A deliberate `DB::statement()` written to bypass the
listener would succeed. **The guards stop accidents, not intent.**

Separately, and unchanged by this decision: any process running as the operator's user — an `npm
postinstall`, a build tool, a compromised dependency — can connect as `root` and read every table.
Loopback binding does not prevent this; only a password would. This is the machine's pre-existing
state, not a condition the Lab creates.

The compensating controls that remain binding:

- **FileVault** — non-waivable, and what protects the 2.2 GB copy at rest.
- **`bind_address = 127.0.0.1`** — the host is not reachable from the network.
- **No PII in the Lab database** — `results.user_id` is read and never stored; P1's ETL converts it
  to `student_ref` on the way in.
- **The copy never enters this repository** and never leaves this machine.

## Why the write-block survives a disposable snapshot (2026-08-23)

The operator's position, recorded the same day: this is a development machine, the snapshot is a
disposable copy, and they are free to do anything with it. That is true, and it is why there is no
local backup requirement anywhere in the program (core plan §14.6).

It does **not** retire guards 1 and 2. Their value here is no longer primarily a compliance one — it
is that an accidental write corrupts the snapshot mid-analysis and costs a 2.2 GB re-import and the
hours around it. The guards are cheap, already built, and already passing. They stay.

## Re-evaluation triggers

Any one of these makes the trade-off invalid, and this ADR must then be superseded:

- A second human account, or shared/remote access (SSH, screen sharing, remote management).
- The database is loaded onto a machine that is not single-operator.
- A project on this machine begins running untrusted third-party install scripts against the same
  MySQL instance.
- Port 3306 stops being loopback-only.
- The Lab gains a code path that writes to a database it does not own.

## Alternatives considered

- **A dedicated `lab_ro` account with eleven grants** — the withdrawn design. It buys real
  database-level enforcement, and it costs an operator gate, a committed grant file, a re-issue
  obligation on every refresh, and a verification script. Rejected by the operator as
  disproportionate for a single-developer local project.
- **Set a password on `root`** — rejected: breaks 31 unrelated local projects, recurring cost on
  every new clone, no gain against the actual threat model.
- **Socket authentication (`auth_socket`) for `root`** — not evaluated; it would harden the account
  without touching any `.env`. The preferred option to revisit if a trigger above fires.
