# ADR-023: A destructive-command guard protects `injazedu_lab`, and tests get their own database

**Status**: Accepted
**Date**: 2026-08-27
**Decided by**: Operator
**Evidence**: a destructive artisan command run in a past session wiped real, manually-imported
data in `injazedu_lab`, including the `users` table

## Context

`apps/lab/tests/` had no isolation from the developer's real Postgres database. `phpunit.xml`
pointed the *default* connection at sqlite `:memory:`, but left `DB_HOST`/`PORT`/`USERNAME`/
`PASSWORD` unset and there was no `.env.testing` — so the `pgsql` connection fell straight through
to `.env`, i.e. `injazedu_lab`. Because Laravel's native `vector` column has no sqlite equivalent, a
Phase-0 research note (`specs/003-service-health-guardrails/notes.md` N4) had already established a
workaround — repoint `pgsql` at `injazedu_lab` inside each test's `setUp()` — which fifteen Feature
test files then copied.

No test in the repo ever ran `migrate:fresh` or `RefreshDatabase`, so the checked-in suite could not
by itself have caused a full wipe. The actual incident matches a destructive artisan command
(`migrate:fresh`, most likely) run directly against the only database that was ever configured —
plausible because CLAUDE.md and the constitution describe the Lab database as "reproducible" /
"disposable," language written to justify *not requiring backups* (§14.6), but easily misread as
license to reset it. There was no technical guard anywhere preventing that.

## Decision

1. **A dedicated, disposable `injazedu_lab_test` Postgres database** (same container, `pgvector` +
   `pg_trgm` enabled) that `apps/lab/.env.testing` points every `pgsql` connection detail at.
   `phpunit.xml` no longer overrides `DB_*` at all — it would otherwise shadow `.env.testing`, which
   is exactly the gap that caused this. `tests/TestCase.php` uses `RefreshDatabase`, safe now that
   `pgsql` under `APP_ENV=testing` can only ever resolve to the disposable database.
2. **The mirror/guardrail tests are split by what they actually need**, not left as one suite:
   - Seven that check schema shape or their own scratch tables — `ProfileDeclarationTest`,
     `NoRawAnswerRowsTest`, `NoUserIdAnywhereTest`, `VectorProbeSchemaTest`, `CopyGuardTest`,
     `NoPiiInLabSchemaTest`, `BatchUpsertIdempotencyTest` — need no real data and stay in
     `tests/Feature/`, now running against `injazedu_lab_test`.
   - Eight that assert facts about the real imported mirror — `StatisticReproducibilityTest`,
     `InventoryMetricsTest`, `SourceResultsCompletenessTest`, `StatsReproducibilityTest`,
     `ValidationReconciliationTest`, `ImportIdempotencyTest`, `ImportResumeTest`,
     `ImportQueueParityTest` — move to `tests/Validation/` (`Tests\Validation\TestCase`, which
     deliberately does *not* use `RefreshDatabase`), registered as phpunit's `MirrorValidation`
     testsuite. `composer test` runs only `Unit,Feature`; `composer test:mirror` runs
     `MirrorValidation` explicitly. Every write in that suite is now inside a transaction that is
     rolled back (`ImportIdempotencyTest`'s two previously-unguarded methods were the gap).
3. **An executable guard**, not just a convention: `AppServiceProvider::guardDestructiveCommands()`
   listens for `migrate:fresh` / `migrate:refresh` / `migrate:reset` / `db:wipe` and refuses them
   (`App\Exceptions\DestructiveOperationBlocked`) unless the resolved database is in
   `config('lab.safe_destructive_databases')` (default: `injazedu_lab_test` alone).
   `guardDestructiveStatements()` does the same for a raw `DROP DATABASE`/`DROP SCHEMA ... CASCADE`
   on the `pgsql` connection — the same `beforeExecuting` mechanism ADR-021 already trusts for the
   `injazedu` read-only guard. Verified in `DestructiveCommandGuardTest` against a synthetic,
   never-connected database name — never against `injazedu_lab` itself, so the test cannot
   reproduce the incident it guards against.
4. **CLAUDE.md and the constitution (§III) are amended**, not just the code: "reproducible" is
   scoped explicitly to the *schema*, not to manually-imported data, and both now say plainly that
   `migrate:fresh`/`db:wipe`/`DROP DATABASE` against `injazedu_lab` needs the user's confirmation
   regardless of what "reproducible" says elsewhere.

## Consequences

- `composer test` can never touch `injazedu_lab` — not through a forgotten `RefreshDatabase`, not
  through a stray `config()` call, because nothing in that suite references the literal string
  `injazedu_lab` any more.
- `composer test:mirror` remains slower and requires `lab:import`/`lab:profile` to have already run
  — unchanged from before, just no longer bundled into the default test run.
- The guard is a backstop, not a substitute for asking. It stops the mechanism this incident
  actually used; it does not make destructive operations against real data something to decide
  without the user.
- The MySQL `injazedu` connection needed no new guard: its existing empty-write-host list and
  `beforeExecuting` SELECT-only check (ADR-021) already block every destructive statement, and no
  migration ever targets that connection.

## Alternatives considered

- **Rely on documentation alone.** Rejected: this is exactly what failed. "Reproducible" already
  existed in writing and was misread as license to reset.
- **Move all fifteen tests onto `injazedu_lab_test`, re-importing fixtures there.** Rejected for the
  eight validation tests: their own docblocks state they intentionally validate the real mirror
  against the real MySQL snapshot (`SourceResultsCompletenessTest`, `StatsReproducibilityTest`) —
  moving them would either make them meaningless against synthetic data or double the import cost
  the operator explicitly does not want to pay repeatedly.
- **A blanket `DB::prohibitDestructiveCommands()`.** Rejected: it is a boolean gated on
  `app()->isProduction()`, not scoped by database name, and it also touches plain `migrate`'s
  confirmation prompt — too coarse for "safe against this one specific database."
